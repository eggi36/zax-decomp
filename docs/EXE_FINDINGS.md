# Findings from Zax.exe

Static analysis (strings, references in the machine code, disassembly with `objdump`). The exe was not executed.

`Zax.exe`: PE32, Intel 386, GUI, image base `0x400000`, 2,572,288 bytes. Sections `.text`, `.rdata`, `.data`, `.cms_t`/`.cms_d` (remains of the copy protection, see "Exe variants"), `.idata`, `.rsrc`. No RTTI type names.

**Default key bindings** (`0x59c550`, section `[No Joystick Control Configuration]` in `Zax.CFG`) [confirmed 2026-10-20]: every action gets a scan code (numbering like DirectInput `DIK_*`), e.g. Zoom In `0x4E` (keypad +), Zoom Out `0x4A` (keypad −), Zoom Reset `0x37` (keypad *). The default does not assign Ü, Ö and Ä (scan codes `0x1A`, `0x27`, `0x28`); in the VM's `Zax.CFG` the zoom is put on them. The zoom keys only work when held for a while: tapped briefly (60 ms) nothing changed, held for 2 s Ö zooms in and Ä zooms out (further than the initial level); Ü changed nothing at the initial level, so it is probably Zoom Reset [verified 2026-10-20, VM helper `{"hold": "OE", "seconds": 2}`]. The helper also knows the default keypad keys as `NUMADD`, `NUMSUB` and `NUMMUL`.

**The binding keys of `Zax.CFG` are in the game's language** [confirmed: code; verified 2026-11-11 with the original exes]: the key's two words (`"%s %s"`, `0x60fc70`) are the binding's category and name as `Game_DefaultKeyBindings` `0x59c550` gives them, the game object's statics `0x713e40`–`0x713f04` (e.g. `0x713e6c` "General", `0x713e68` "Move Up"), which are `LocalString`s (`LocalString_Ctor` `0x501030`): `ZLocalTable::Load` translates every registered string in place when `Local.txt` is read. So an edition with a `Local.txt` (in its `.RED` pack, or the Russian edition's loose `local.txt`) reads and writes its own words: `Ogólnie Góra` (Polish, Windows-1250), `Информация Движение вверх` (Russian, Windows-1251), `General Arriba` (Spanish), `Allgemein Aufwärts bewegen` (German with `GERMAN.RED`), the game without a pack `General Move Up` [confirmed: the four `Local.txt` pairs]. The weapon bindings' names are plain strings (the item names; Polish 1309 patched them, "Exe variants" below), so those keys only change with that patch. The section is not translated with a `Controler ID Number` of 1 or more: it is the joystick object's name, the plain "No Joystick" (`0x6171d0`, `Joy_Init` `0x4dda00`); only without a joystick object is it the translated "NO JOYSTICK" (`0x6bd568`) [confirmed: code; not run]. The consequence: a `Zax.CFG` does not carry its bindings across languages. Bindings written by the game without a pack are not found by a localised edition (or by the same game with a pack added) and the other way round; the game silently uses the defaults for every key it does not find. Evidence: a `Zax.CFG` with the English keys (Move Up/Down = scan codes of Z, Y) and the localised keys (A, S) in `[No Joystick Control Configuration]`, and the localised keys once more (D, F) in `[<translated NO JOYSTICK> Control Configuration]`, files only for the job (`--cleanup`), x86 VM: the original Russian 1308 (the VM's `Zax.exe` = the Russian one, with the Russian `local.txt` and `DATA.dat`; job `20261111-001548-b02e`) and the original Polish 1309 (its `Zax.exe` and `Polish.red`, the launcher of zax-launcher; `20261111-002547-115e`) both show A and S on the controls screen (the file fetched while the dialog was open: unchanged). The port does the same (the Russian with the i386 exe `20261111-002416-e475`, the Polish 1309 with the x64 exe as an outside job `20261111-002209-e431`: A and S). Results outside the repository in `runs/keysfile/`.

In addition, the exe opens `Local.txt` at start (`0x4cdbbb` in `Game_Startup` `0x4cd780`) [confirmed: code; VM, `reimpl/src/app_start.cpp`]. The file only exists in localised editions, in the archive `GERMAN.RED`. It translates the fixed texts of the exe in pairs `ENGLISH: …[END]` / `LOCALIZED: …[END]` (FORMATS.md 1 and 2.3).

**Direct start** (`zax-launcher/`) [verified: VM, `Eigene/Level 1` starts directly]: the exe has no ASLR (`DllCharacteristics = 0`), all addresses are fixed. `Zax-Launcher.exe` starts Zax.exe suspended, loads `Zax-Launcher.dll` via `CreateRemoteThread(LoadLibraryA)` and then lets it run; Zax.exe on disk stays unchanged. A replacement `winmm.dll` was rejected: system DLLs in the process (e.g. DirectSound) also use winmm and would then get the replacement DLL, which would have to forward all their functions. The DLL checks the 6 call sites of the main menu constructor (`0x50eab7`, `0x59bace`, `0x59d320`, `0x5a102d`, `0x5ba8ef`, `0x5bff30`; each `E8` to `0x5be4a0`) and redirects them to itself. The first main menu is created at the end of loading the game data (`App_LoadGameData` `0x5a01c0` → app slot 33 `World_OpenMainMenu` `0x59bab0`). Since 2026-10-29 the DLL then points slot 3 of the application's vtable (`0x602dd4`, the step `0x59d140`) at itself for one call: the main loop runs the steps (slot 3) before drawing (slot 4, `App_RunSteps` `0x4cdd80`), so the map starts before the main menu is ever drawn, and the menu's song is not streamed (debug log: `Start New Game` directly after `Load Game Data`, before about 330 ms later behind a `Stream sound`) [verified: VM, runs `20261029-061339-e926` (new) / `-061340-3b6c` (before), with the reimplementation `-061604-1204`]. A thread timer (300 ms; the main loop `0x599910` fetches all messages with `PeekMessageA(…, NULL, …)` and passes `WM_TIMER` to `DispatchMessageA`) stays as the fallback when the slot does not hold `0x59d140` (a later phase-6 build with its own vtables); the first step kills it, so a normal start sets no thread timer that fires (a replay of a recording made with the timer still running had to stand in for it with another procedure). In the first step or the timer: look up the difficulty by file name in the catalogue `0x6c2a00` (name via vtable `+4`, with folder and without extension, e.g. `Dificulty Types/Normal`; order Easy, Hard, Normal) [verified], `0x5bb780`, `0x5a3180("QuestMode")`, `0x51e450`, then `StartNewGame(1, map, start point, 0)`; without `/Spawn`, `First Map Spawn Point` from `CRules` is passed (like the base with an empty map). Afterwards clear the menu's return target (`0x404180(0)`) and close the menu (vtable `+0x14`, deletes the object), like the difficulty dialog.

**"Load Map" button** (`zax-launcher/`) [verified: VM, appears between "Save Game" and "End Game", loads `ACT 3/M16/16 Drill Hydro`]: at start the exe creates the label `"Load &Map (F9)"` as CString `0x7144d4` (initialiser `0x5bd9c0`), but never uses it; this is the game menu's missing button `[+0x13c]`. Buttons are always created the same way there: `0x417710` (operator new, size `0x138` in ecx), `0x40fa60(menu, CString *text, 0)` (`ret 0xc`), `0x40c7c0(button, placement, 0, x, y, 0)` on the menu (`ret 0x18`; the other buttons use placement `8` and `-1000, -1000`). `Zax-Launcher.dll` replaces the first 5 bytes at `0x5bfe14` (`mov ecx,0x138` at the start of "End Game") with a jump, creates the button this way and stores it in `[menu+0x13c]`; then the constructor continues normally. Condition as for "Save Game": not as a multiplayer client (world vtable `+4`, then `+0x34`). The dialog's "Ok" sets the difficulty from its selection and calls `StartNewGame(1, map, 0, 0)`, i.e. without a start point (the base `0x4f4e70` only replaces both values from `CRules` when the map is empty). The player then appears at the `Spawn Point Name` from the map's `Team Info` [verified]. In about 50 maps that is the developers' start point `cheater`: among other things its Spawn Action activates the objects `cheater gun`, i.e. inactive weapons and equipment next to the start point (in `16 Drill Hydro`: autogun, Twin Disrupter, rocket launcher, mines, battery, shield). The dialog does not ask for a difficulty, the previous one stays; the "Game Type" selection is set to "Default For Map".

**Other hidden buttons** [confirmed: Zax.exe, search over all click handlers]: we looked for handlers that query a button that no constructor of their class creates. ## Level cache ("Return to map")

On a level switch (`0x59b400`, virtually via `+0x1c0` of the world) `Return to map` of the `CSwitchMapAction` decides what happens to the level **left behind** in the cache (object `[world + 0x33c]`) [confirmed: Zax.exe]. Enumeration at `0x625388`:

| Value | Text | Effect in the code |
|---|---|---|
| 0 | `Invalid setting!` | error message "Invalid Map Caching Directive …" (`0x5a55b1`), the switch happens anyway |
| 1 | `definitely soon` | nothing – the level stays in the list of loaded levels |
| 2 | `probably soon` | stays loaded, moves to the end of this list (`0x589a50`) |
| 3 | `unlikely soon` | taken out of the list, into the release list (`0x589790`) – the same function as `CFlushMapAction` |
| 4 | `never` | expires (`0x589570`, message "Expiring map that was already expired") – the same function as `CExpireMapAction` |

Consequence for the editor: the choice affects memory and loading time when returning. Whether `never` resets the level's state when returning (enemies back) is unverified in the game.

**The commands are not reachable: the whole cheat module is compiled out** [confirmed: Zax.exe code and scans 2026-10-30 (rel32 callers, dword and disp32 scans re-run by the parent session); the design from Star Trek: Away Team (Reflexive, March 2001, the same engine), whose module is complete, see below]:

- The registration function `0x46cd50` is only `ret 8`, folded by the linker with `CObject_OnMessage` and other empty slots (40 rel32 callers, many vtable references). Its body was compiled out, not the calls to it: the 19 call sites in `CZaxApp_Ctor` with their strings and routines remain. (Until 2026-10-30 this read "an empty function folded together by the linker … the debug version apparently had code here"; the fold is right, but the empty body is a compiled-out member, see the comparison.)
- The rest of the module is gone too. `StaticInit_46cd30` only registers `StaticExit_46cd40` with `atexit` and no longer clears the list head. `0x46cd40` is a single `ret` instead of freeing the list. The matcher function does not exist: `0x46cd40` is followed directly by `0x46cd50`, and a byte-pattern search for its loop finds nothing in Zax.exe.
- The table `0x6bd2dc` has exactly 19 references, the `mov ecx, 0x6bd2dc` before the 19 calls; nothing reads or initialises it.
- The input hook that would have fed the commands is still there, but empty. `Keys::AddChar` `0x4e2a00` (the key table at `0x6c1050`; callers `0x599a0c`, `0x599a25`, `0x599a92`, from the window messages) calls a character filter stored at +0x818 (function) / +0x81c (`this`) before it queues a character (`0x4e2a0c`, `0x4e2a16`). Nothing writes that slot: a dword scan for `0x6c1868`/`0x6c186c` finds 0 hits, and a disp32 scan for 0x818/0x81c finds only these two reads. It stays 0, and `AddChar` skips it.
- The routines themselves have no callers and no references other than the `push` at registration; no key triggers them.
- The text "Chat" next to the commands is only the name of a key binding (`0x59c223`), no connection to the cheats.

**How it worked** (Away Team's complete module, the same functions in the same order; `StaticInit_46cd30`, `StaticExit_46cd40` and `0x46cd50` are their compiled-out counterparts) [confirmed: code of Star Trek: Away Team; for Zax an assumption that the debug build had the same]: `Add(text, routine)` puts an entry {text, routine, next, cursor} at the head of the list and installs the matcher as the key table's character filter (+0x818/+0x81c). The key table gets every `WM_CHAR`/`WM_SYSCHAR` character of the game window, on any screen.
The matcher compares each character case-insensitively (`toupper`) with each entry's next expected character. It advances that entry's cursor or resets it to the start (the wrong character is not tested again), and calls the routine without arguments when the text is complete. It always returns 0, so the typed characters still reach the game. There is no chat line, console or Enter: the command is just typed.
Away Team also gates its commands: `CHEATER` toggles a global flag (only during a running mission) that `IWIN` and `MEDIC` check. Whether Zax's routines had such a gate cannot be seen, because they test no flag themselves [assumption].

Consequence: the cheats do not work in the chat window (multiplayer only) or anywhere else, and the original has no other way. Bringing them back means rebuilding the matcher and installing it as the filter at `0x6c1050`+0x818; the launcher's `/Cheats` (Ctrl+F1 … F9) is the existing workaround.

**Every candidate path checked, 2026-10-28** [confirmed: code, Zax.exe; no VM test needed, no path exists]:

- **The "list" `0x6bd2dc` is not even an object.** It is a 4-byte slot in `.bss` between CChasePursueAI's class variable (`0x6bd2d8`) and the demo-record bytes `0x6bd2e0`/`0x6bd2e4`/`0x6bd2e8` (see "Other unused leftovers"). No static initializer constructs it, no vtable is written to it, and apart from the 19 `mov ecx, 0x6bd2dc` nothing in `.text` names any address `0x6bd2dc`–`0x6bd2df`. A class whose members and method bodies were compiled out by a debug switch leaves exactly this (an empty object of size 1, padded to 4) [assumption: the developers' build switch, not visible in the release]. The registration call `0x46cd50` is the linker's folded `ret 8` (the same address is CLayerPartAI's slot 25, CObject's slot 0 and the player AI's debug slot 41, which is why `docs/exe_symbols.csv` calls it `CObject_OnMessage`).

- **Demo build**: the same, see "Demo (build 950)". `Zax_Demo.exe` is not in `gamedata/`; the finding there is from the earlier analysis.
- **How they were meant to be used** [assumption: the developers' intent; the lookup code is missing]: the names are typed text with alternative spellings with and without a space ("give all", "show map", "kill me"), and one help text of the release still refers to a cheat by its typed name: the mini map's opacity field says "doesn't affect "hidefog" cheat" (`0x619740`, `hud_classes.cpp`). A prefix cannot be determined: the lookup code does not exist in either build. `showmap`/`hidefog` are empty in the release (`0x58ea40`), so even their routines were compiled out; their effect (mini map without fog) is only known from that help text.

## Game speed texts and the frame step

[confirmed: code, Zax.exe, 2026-10-28]

- **The texts**: "     Normal Speed     " (`0x627528`), "      1/%s Speed    " (`0x627540`), "   %s Times Normal  " (`0x627558`) and "&Tinker" (`0x6274b0`) are each copied into a global `ZString` by a static initializer (`0x5bdb70` → `0x7144e4`, `0x5bdba0` → `0x714508`, `0x5bdbd0` → `0x714524`, `0x5bda80` → `0x714528`) and freed at exit. The only references to the four globals (and to `0x7144d4` "Load &Map (F9)", `0x714550` "&Editor (F6)") are these two functions each. Unlike the game menu's other entries (`LocalString_Ctor` `0x501030`, translatable) they are plain `ZString`s (`0x4dee00`), i.e. never meant for `Local.txt` [assumption: debug menu of the internal build, the developers' code; the padding with spaces suggests a fixed-width label, e.g. of a speed slider].
- **No time scale exists.** The frame step `App::RunSteps` `0x4cdd80` takes the real time since the last frame (QueryPerformanceCounter `0x53d150` / frequency `0x53d170`) plus the rest of the last frame, capped at `+0x5c`, and runs world steps (slot 3) of at most `+0x58` seconds while at least `+0x54` is left. The three values come only from `World::Ctor` → `Game_Startup` `0x4cd780` (`0x4f0799`…`0x4f07a3`): `+0x54` = 1/90 s (`0x3c360b61`), `+0x58` = 1/30 s (`0x3d088889`), `+0x5c` = 1/6 s (`0x3e2aaaab`). No factor is applied anywhere in between; slot 3 (`0x4f2620`) passes the seconds on unchanged.
- **One dormant mode**: `+0x1d` ("run on the clock"; only writer `0x4cdbe0`, always 1). With 0 every frame would run exactly one step of 1/30 s regardless of the real time (frame-locked; at 60 fps the game would run twice as fast). Not settable.
- **The only speed-related control in the game is the pause** (`0x59d5c0`: key binding `0xf` while the game type's slot 34 allows it toggles the application's `+0x360`).

Follow-up for the launcher (not built): a speed switch would scale the elapsed time in `App::RunSteps`, e.g. by hooking `0x53d150` (or the reimplemented `App_RunSteps`) and multiplying the difference to the previous counter. Values below 1 are safe; above 1 the cap `+0x5c` and the step `+0x58` limit the effect (more steps per frame), and the physics step stays 1/30 s.

## Deploying devices (Companion Drone, Autogun) and projectiles

Examined 2026-10-21 with REA/Ghidra and disassembly, because a drone placed in the level does not follow Zax and a placed mine does not detonate (OPEN_ISSUES, "Template object in `.mdl`").

- **Create an object from a model** `0x5176f0` [confirmed] (thiscall on `0x6cfdd8`, 5 arguments, `ret 0x14`): `(model, fallback class, creator, …)`. Copies the model's default object; if the model has none, it creates an object of the fallback class. Always sets `Stationary` (vtable `+0xe8`, mask `0x200000`). For `CEntityAnimated` it then sets vtable `+0x1a0` with its own value `+0xc8`. At the end it sets `Created By` = creator (vtable `+0x114`).
- **`Created By`** is `CEntityAnimated+0xd0` [confirmed: registration `0x48e262`, type 3 = reference to an object]. vtable `+0x110` reads the field (`0x48f190`: `mov eax,[ecx+0xd0]`), `+0x114` sets it (`0x48f1a0`). In all original levels `Created By` is empty [verified: `grep` over all `.zax`].
- **Deploying** `0x47a0f0` (`CUndeployedInventoryItem`, argument = owner) [confirmed]:
  - It creates the item definition's `Projectile` model via `0x5176f0` with the owner as creator.
  - It places the object at a free spot within 500 next to the owner (`0x4eb7b0`, 500.0 = `0x43fa0000`).
  - If the device's stored damage is greater than 0, it subtracts hit points (vtable `+0x18c`, with `Unavoidable`).
  - Then it puts the `CDeployedInventoryItem` of the `Ammunition` into the inventory: `+0x18` = object ("Deployed Entity"), `+0x1c` = owner ("Owner").
  - The message texts ("Trying to deploy a CUndeployedInventoryItem …") exist as global CStrings, e.g. `0x6bda48`.
- **`CCompanionAI`** (vtable `0x5efef0`, factory `0x46e120` (new `0x10c` bytes)) [confirmed]:
  - At its start (vtable `+0x60`, `0x46e800`) it remembers its own object (`+0xe4`) and that object's `Created By` as owner (`+0xcc`), but only if that is a `CEntityWalking`.

  - Every tick (vtable `+0x64`, `0x46e890`) it looks for a spot near the owner every `Time Between Rechecks` (`0x46ead0`: random angle 0 … 2π and a distance between `+0xdc`/`+0xe0`, `Move/Minimum Distance`/`Move/Maximum Distance` (defaults 25 and 50)) and walks there.   - Consequence for the editor: a placed drone only follows if its `Created By` points to the player character when loading. ## Class and field registration (basis of `zax-formats/zaxtools/exeschema.py`)

At program start every class registers itself and its fields [verified]:

- `0x415780` register a class: `(&class variable, "CName", f32 version, parent class, size, factory …)`. The parent class comes as a class variable (`mov reg, [X]`) or via a getter function (`mov eax, [X]; …`). 495 classes.
- Field: `operator new` (`0x5d033a`), then a **type-specific constructor** with `"Category/Field name"` as the last argument (before it offset, size, default value, value range), then `0x415700` "add field to class" on a class variable (`mov ecx, [X]`) or on the result of a class getter (`call getter; mov ecx, eax`; until 2026-10-28 `exeschema.py` missed the getter form and gave the first fields of 10 classes to the class before, e.g. the six frame/scroll bar fields of `CMissionOverWindowOptions`). The order of the calls is the order in the text and binary formats. 1,639 fields, the same lists as `docs/fields.csv` [confirmed: self-test].
- `0x54da60` enum value (`value, "name"`, e.g. `-1 = Nutral`, `-1 = None Selected`) – also after adding; `0x419020` help text (usually on `ClassInfo_LastField` `0x415770`, see "Developer messages and help texts"); `0x419030` old field name.
- Type = constructor address, e.g. `0x54dfc0` bit flag (1 byte), `0x415dd0` text, `0x54ecd0`/`0x54ec40` float, `0x54d7f0` enum, `0x4186f0` object pointer, `0x54e690` embedded object, `0x419230` array, `0x417930` named array, `0x547fd0` polygon. Complete list: `ENCODING` in `exeschema.py`.
- The base class `CObject` only has "Dynamic Properties"; models are `CModel` (version 193).

## Tools for further analysis

On Linux `objdump -d -M intel --no-show-raw-insn --start-address=0x… --stop-address=0x… Zax.exe` is enough. File offset = VA − 0x400000 for `.text`, `.rdata` and `.data`. To find uses of a string, search for its VA as a 4-byte value in the code (usually `push imm32`, opcode `0x68`).

## Music: which of a level's three songs plays [confirmed: code, 2026-10-28]

A level's `CMusicMixerData` (the level header, replaced by `CSetMusicAction`) names three songs of the music folder list `0x6c0f10`: track 0 "Full Mix Song", track 1 "Med Mix Song", track 2 "Ambiant Song" (sic), plus "Num Seconds To Switch" (cross-fade time, default 5). The game picks the track itself every frame:

- Every enemy figure (category enemy) with a `CSkeletonAI` sends a `CSkeletonUpdatedMessage` (`0x5788a0`, id `0x713670`) to the world on each AI update (`0x576730`); the world's message slot (`0x59d110`) counts them in `0x713f1c`, which the frame clears.
- At the end of `CZaxWorld`'s frame (`App_Frame`, `reimpl/src/c4_app2.cpp`), with `0x713f20` the seconds since the last switch to Full or Med and 10 s the constant `0x5eecd8`:
  - 4 or more counted → track 0 (timer reset);
  - 2–3 counted while track 2 plays → track 1 (timer reset);
  - fewer than 4 while track 0 plays and more than 10 s since the last switch → track 1 (timer reset);
  - 0–1 counted while track 1 plays and more than 10 s since the last switch → track 2;
  - otherwise unchanged.
- `MusicMixer_SwitchTrack` `0x51e520`: the same song on the new track changes nothing; otherwise the stream cross-fades over "Num Seconds To Switch"; a switch during a fade is queued; a song that ends starts again. `CSwitchMusicTrackAction` sets a track directly, but the rule above may change it again in the next frame. The main menu plays track 2; `Rules.txt` "Startup Song" is the start's menu music.
- Open: whether every enemy of the level updates its AI each frame or only those near the view (so whether "counted" means "on screen"). The names full/medium/calm are our reading of the field names [assumption].
